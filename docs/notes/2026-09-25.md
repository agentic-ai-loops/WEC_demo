# Task 2: The document for design

Refer to @01-businessdata.md for the business data models
Refer to @02-graphql-api.md for the data extraction mechanism

In this task, we want to compose the design document for #design.

The top-level specs are:

1. we focus on generating client-side content only: html + js + css + resources
2. the #design template is a directory containing one or more files.
  - jinja templates for html, js, css
  - static assets (html, js, css, images, raw files)
  - graphql queries to hydrate the templates during rendering
  - serialized metadata and configuration models

## Design directory structure

The directory structure mirrors the next.js convention for directory based routing.  See example:

```
<top-design-folder>
  - _layouts/base.html.j2   # full jinja2 template engine features supported
  - _partials/...           # jinja2 features are supported
  - _config.json            # 
  - site.gql                # fetch data every page needs
  - page.html.j2            # gets data from the sibling page.gql result
  - page.gql                # retrieving from graphql endpoint during rendering time
  - hero.png                # static resource
  - style.css.j2            # styling
  - products/
    - page.html.j2          # page for the uri /products/
    - page.gql              # gql to hydrate
    - [slug]/               # dynamic route segment
      - page.html.j2        # gets the page.gql result, plus `slug`
      - page.gql            # access `$slug` as a graphql variable.
      - params.gql          # gql to obtain the list of `{"slug": ....}` params.
      - [id]/               # dynamic routing may be nested
        - page.html.j2      # gets `slug` from context, and `id` parameter
        - page.gql          # has `$slug` and `$id` graphql variables
        - params.gql        # has `$slug` variable, and lists `{"id": ...}`.
```

- The site data comes from `site.gql`
- The page specific data comes from `page.gql`
- Dynamic segments are obtained from `params.gql`

More details on gql results:

`params.gql`:

```
{
  ...: [
    {
      <segment_name>: "..."
    },
    ...
  ]
}
```

## Rendering

We use python Jinja2 rendering engine.  Therefore, all jinaj2 modularity features are supported with reusable fragments in `_layouts/...` and  `_partials/...`.

The target is web content (html, css, js, assets) in a `_site/` output directory.

The rendering process:

-  page.html.j2 -> run page.gql(params) -> <out>/index.html
-  other *.j2 -> <out>/<name>
-  other files -> copy to <out>

site.gql run once before the render walk.

Site rendering should be atomically, so _site is updated only when the entire site renders without error.

Jinja2 runs in sandboxed environment.
